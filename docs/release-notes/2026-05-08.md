# Release notes — 2026-05-08

A single-day audit-driven push: 22 pull requests covering performance, reliability, security hardening, observability, tests, and documentation across every major module (hub, OCR, backup, customer, reconciliation). Every fix has a regression-test or comment-block recording the *why* so future-you doesn't reintroduce the bug.

This isn't a normal release cadence — most days are calmer. It's the result of a sequence of external module reviews (OCR, backup, customer, reconciliation) plus a cross-codebase performance audit. Each batch came in, got triaged, and shipped as separate small PRs to keep the merge units reviewable.

## Review-cycle notes

Every PR went through Codex automated review. The cycle this taught us:

- **Force-push during CI causes false-positive secret-scan failures** (gitleaks can't compute a diff against a rewritten commit). Cosmetic; ignore the notification when the current HEAD is green.
- **`logError` is sync I/O on every call** — calling it on hot paths is a production performance regression. Telemetry on per-keystroke endpoints belongs in an in-memory bucket pattern (like `securitySignals`), not in `logError`.
- **`res.send`/`stream.on('end')` are NOT flush-to-client signals.** Audit success has to hang off `res.on('finish')`; lifecycle listeners must be attached *before* awaits that span seconds (snapshot, hash) so a disconnect during pre-stream work still gets recorded.
- **`db.transaction(...)` nesting via savepoints is your friend.** Wrapping outer code that calls into already-transactional helpers does the right thing — the inner txn becomes a savepoint inside the outer transaction.
- **Codex catches the kind of subtle stuff humans miss.** Several P1-flagged regressions tonight were "this looks fine but actually..." catches that would have shipped without review. Worth keeping in the loop.

## What shipped (chronological)

### Hotfixes for merge-loss bugs

A recurring failure mode in this window: a PR's diff includes a feature AND its supporting infrastructure (migration, schema CHECK, import statement), then a parallel merge silently drops one half of the diff during conflict resolution. The feature ships pointing at infrastructure that no longer exists, the runtime contract is broken, and nobody notices until a downstream operation hits the missing piece.

- **#221 hotfix: SiteCard accpac vars + helper lost in #200/#198 merge** — the per-site accpac freshness fields the dashboard tile relies on were in #198's diff but dropped during the #200 merge; restored.
- **#223 hotfix: restore backup.js imports lost in #210/#211 merge — service was crashing on boot** — `logError` and `rateLimit` imports were in #210 and #211 separately, both got merged, neither retained the imports. The service crashed on every boot of 2026.5.2 with `ReferenceError`. Restored.
- **#228 fix(hub): restore lost v62 migration (last_accpac_synced_at columns)** — the v62 migration adding three columns to `hub_sites` was in #198's diff but lost during the #198 → #200 → #214 merge sequence. Production hubs upgrading to 2026.5.2 hit `no such column: last_accpac_synced_at` on every `hub.sync` tick, which cascaded into `fetch failed` / `aborted` entries that masked the real cause. Restored. The follow-up commit also adds the columns to `schema.js` `CREATE TABLE` so fresh installs aren't gated by the migration's `hubSitesExists` check.
- **#235 fix(audit): drop resource_type CHECK constraint that silently swallowed audit rows** — #198 added three `logAudit` calls passing `resource_type='site'` for the Sync from Accpac flow, but never updated the CHECK constraint that whitelisted `('user','connection','record','rule','system')`. Every operator click and every scheduled retry hit `SQLITE_CONSTRAINT_CHECK` and the audit row was silently dropped. Migration **v65** drops the CHECK entirely (table-swap dance — SQLite has no `DROP CONSTRAINT`); resource_type is descriptive metadata, not a foreign-key invariant. The status CHECK (`success|failure`) stays.

### Updater (the worst of the bugs)

- **#234 fix(updater): stop wiping the service mid-install + restore the delta path** — two compounding bugs:
  1. `installer.nsi` removed the service via `nssm remove` BEFORE extracting new files. Any failure between (file lock, AV scan, NSIS timeout, `nssm install` exit non-zero) left the service permanently gone with no recovery — the wrapper PowerShell's "start service if not running" check is a no-op when the service no longer exists. **This is what wiped sites during the 2026.5.3 rollout.** Now: stop service → extract → `install`-or-`set` to bring it back into known-good config. Mid-extract failure leaves the prior service registered and recoverable.
  2. The `lock_hash` was computed against the entire `package-lock.json`, so `npm version` rewriting the version field flipped the hash on every release. The in-app updater rejected delta on every build and fell through to the heavy NSIS installer that contained bug (1). Hash a normalized view of `packages` instead, with the root entry's `version` stripped. Pure version bumps now qualify for delta. **One more release will still take the full installer path** (existing `.lock-hash` files were written with the old method); from then on, "quick update" actually works.

### Hub

- **#222 fix(hub-search): abort stale fetches** — clearing the search input could be repopulated by an in-flight fetch's response. Abort on input change.
- **#236 fix(bat): single source of truth for last-paid-week (site UI + hub tile cannot diverge)** — site `/api/bat/week-status` and `/api/reporting/bat-summary` had parallel SELECTs computing the same conceptual value with different scoping. Result: site UI showed `W10/2027` while the hub tile showed `W44/2026` for the same site at the same moment — both phantom values. New shared helpers `getLastPaidSageWeek()` and `getLastBatReconciliationWeek()` route both endpoints through one source-of-truth query, so the hub-mirrors-site invariant is encoded in the call graph, not in two queries that happen to agree today. Same fix tightened the year+1 attribution heuristic in `querySageWeekTotals` (the original `desc_week + 4 < ISO_WEEK(doc_date)` fired for any in-year late posting and was creating those phantom rows). Year-1 threshold preserved unchanged after Codex review caught that the symmetric tightening regressed cross-year-lag attribution (Dec credit notes posted Jan-Feb).
- **#238 fix(hub): stamp last_accpac_synced_at optimistically after a successful trigger** — long-standing operator complaint: clicking Sync from Accpac on the hub runs the actual sync on the site (data flows), but the hub tile's "Accpac sync" timestamp doesn't move. Root cause: the hub waited for a chained `syncSite()` to re-pull kpis from the site to learn the new timestamp. The trigger forward has a 5-minute timeout but `syncSite`'s health check is 10s — on a slow link the trigger succeeds, the actual sync completes, but the chained refresh times out. Now: stamp `hub_sites.last_accpac_synced_at` directly when the trigger response shows at least one successful per-connection sync; the chained syncSite is preserved as best-effort for fresher records / inventory / BAT data.
- **#239 fix(hub): derive trigger-stamp status/error from per-connection results** — follow-up to #238. Codex caught that the optimistic update unconditionally set `status='ok'` and cleared `last_accpac_error` whenever `okCount > 0`, painting partial failures (2 of 3 ok, 1 fails) green. Now derives status from `body.results`: any `!ok` → `status='error'` with the failed connection's name + message; mirrors the site's own kpis aggregation contract.

### OCR pipeline

- **#224 fix(ocr): allow http:// PDF URLs — supplier serves over plain HTTP** — SSRF guard (#207) allowed only `https://`; one supplier uploads via plain HTTP. Allowlist stays the same; just opened the protocol gate.
- **#225 feat(ocr): cascade resilience — engine cooldown, lane retry, regex circuit breaker** — three independent reliability fixes: per-engine cooldown when a provider returns 429/E552 so the cascade doesn't burn 60s × 12 slots × every row on a rate-limited engine; lane recovery retries with exponential backoff so a single transient `new OcrLane()` hiccup no longer permanently retires a lane; regex circuit breaker halts the run after N consecutive `cascade_exhausted` outcomes (engine returned ≥20 chars, regex didn't match) so a regex-pack mismatch on a new supplier doesn't quietly burn through the whole queue.
- **#226 feat: OCR ops tab + session-expiry warning + halt-bypass fix + backup imports** — Operations → OCR tab with live state, counters, recent runs, and log; session-expiry warning popup with continue/logout; halt-bypass fix so the regular Pause/Resume button is hidden when OCR auto-halt is active.
- **#229 feat(ops): hide OCR topics from System Log default view** — OCR diagnostic topics (engine_cooldown_skip, engine_no_match, etc.) dominate the log signal-to-noise ratio when an OCR run is active. Hidden by default; operator can re-enable per-topic.
- **#230 fix(ocr): cap raster width + JPEG output so worker memory stays bounded** — production hub showed RSS climbing to 2.8 GB after 5 rows on a queue of large-format POD PDFs. Cap rendered raster width at 2400px (env-tunable via `OCR_MAX_RENDER_WIDTH`); switch from PNG to JPEG (PNG kept the raster in memory longer, produced ~10× larger payloads); explicit canvas teardown in `finally` to nudge node-canvas's native allocator. Codex catch added in the same PR: NaN-guard the env parse so a malformed `OCR_MAX_RENDER_WIDTH` doesn't propagate NaN into `getViewport({scale: NaN})` and fail every render.
- **#231 feat(ops): Extract button on Recent reconciliations rows in OCR tab** — operator can trigger OCR for a recon directly from the OCR tab without navigating to the BAT page. Three states per row (idle / this row running / worker busy on another row, with auto-handoff so the queued row picks up automatically when the current run finishes). Codex follow-ups in the same PR: disabled when OCR is paused, queued state shows tooltip with the actual auto-handoff mechanism, backend chain via `setImmediate(() => startExtractionWorker(...))` so the "queued" promise actually delivers.
- **#237 fix(ocr): bound the render wedge + verbose plain-English logs** — production 2026.5.3 hub kept wedging both OCR lanes in the render stage with stage-age past 1 minute, RSS climbing back to 2.4 GB within 37s of every recycle. Root: `pdfjs.page.render()` blocks the worker thread synchronously inside node-canvas on certain PDFs; the in-worker 30s timeout cannot fire because JS is frozen. Five mitigations:
  1. Megapixel + height caps in addition to width (`OCR_MAX_RENDER_PIXELS` default 6 MP, `OCR_MAX_RENDER_HEIGHT` default 4000) — width-only capping let tall A3 / banner PODs through at 12+ MP.
  2. Pre-flight viewport reject before `page.render()` — refuses the page with a verbose structured error before handing it to pdfjs, so the operator sees a loud System Log entry instead of waiting 2 minutes for the parent PDF_TIMEOUT.
  3. Per-URL skip set within a run (gated on `stuckStage === 'render'` after Codex review caught that the original gating was too broad and would blacklist URLs on transient API/network incidents).
  4. Lower default recycle threshold `OCR_LANE_RSS_BUDGET_MB` 2048 → 1200; production traces showed RSS climbing back past 2 GB within 37s of a 2 GB-triggered recycle.
  5. Hard `process.exit(1)` at RSS ≥ 3 GB (`OCR_HARD_EXIT_RSS_MB`) so NSSM restarts cleanly when the leak rate beats every other defence.
  Plus a verbose-English log overhaul on every failure path the operator sees in System Log — `bat.ocr.row` render failures, `bat.ocr.url_blacklisted`, `bat.ocr.lane_died_non_render`, `bat.ocr.rss_hard_exit`, and `hub.sync` errors — translating cryptic codes ("fetch failed", "This operation was aborted") into operator-actionable English naming the site/URL, the likely cause, and the diagnostic command to run.

## Lessons (the structural takeaways)

The merge-loss pattern hit four times this window (#221, #223, #228, #235). Each time, a PR shipped a feature with its supporting infrastructure (migration / import / CHECK list) and a parallel merge silently dropped half. Two structural responses are queued for follow-up:

- **CI guard for migration version contiguity** — currently migrations are an array; missing a version isn't caught at build time. A small CI check that asserts `versions === [1..N]` would have caught the missing v62.
- **Schema-as-CREATE-TABLE-not-CHECK pattern** — #235 chose to drop the resource_type CHECK rather than play whack-a-mole adding entries every time a feature introduces a new resource type. Same principle should be applied to other text-domain CHECKs across the schema where possible.
