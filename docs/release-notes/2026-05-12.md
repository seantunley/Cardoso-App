# Release notes — 2026-05-12

A focused release: one new module from the ground up, plus a small new operations view. The JTI Sales Export — previously a Crystal report + Excel macro that one person ran by hand each month — is now an in-app feature that produces an exact-shape `.xlsx` from live Sage data, archives every full-month export, ships archives to the hub automatically, and runs unattended on the 1st of every month.

Twenty-two commits, three new database migrations, ~8,400 lines added. The whole thing is gated behind a new `can_access_jti` permission so only the people who need it see it.

---

## What ships

### JTI Sales Export module

The headline feature. Replaces the long-running "open Crystal, export to Excel, run the macro, email it" workflow with a single screen on the operator's app.

**The basics — generate an export on demand:**

- New **JTI** page in the sidebar (site mode only; hub installs see a different JTI view, described below). Open it, pick a date range, click Generate, the browser downloads `JTI_Cardoso_Sales_<Site>_<YYYYMMDD>.xlsx`.
- Preset range chips: Today / This week / Last week / This month / Last month. Or pick custom from-to dates.
- Address fields (TownCity, Region, Country) pre-fill from saved per-install defaults; you can override them per-export without touching the saved defaults.
- Output structure matches the existing macro output exactly — 14 columns A–N, headers in row 1, Arial 10 font throughout, Date column as integer `YYYYMMDD` with format `"0"`, Quantity formatted `#,##0.00`. Verified against the supplied sample file by an automated golden-snapshot test (skips when the sample isn't present so CI without the .xlsx still passes).
- File size dropped from the macro's 460 KB to ~190 KB (we kept structural shape but moved to ExcelJS's shared-strings table instead of the prior tool's inlined-per-cell strings).

**The Sage side — its own pool, no BAT spillover:**

- New connection role: **JTI export**. Assign a connection to it in Settings → Connections → Module routing. The module reads through its own pool and **does not** fall back to the BAT Sage pool — this was a deliberate decision after a previous accidental cross-module spillover. If no connection is routed, the page shows a yellow banner naming exactly what to click.
- The default SQL is shipped in code; an admin can override it per-install (Query (advanced) panel on the JTI page). Override is validated server-side before persisting: missing required columns (TRANNUM, TRANDATE, ITEM, DESC, CUSTOMER, NAMECUST, QTYSOLD), missing required parameters (`@from`, `@to`), and mutating keywords (UPDATE, DELETE, DROP, etc.) all block the save with structured error messages. A `@vendor` LIKE filter is recommended but generates a warning, not an error, if omitted.
- Sage CHAR padding is trimmed at the SQL layer (`LTRIM(RTRIM(...))` on identifier/name columns; `RTRIM` only on the product description column where leading whitespace is intentional). Same operator-visible fix verified by re-running against the supplied sample — 4,277 of 4,277 rows match between live output and the macro-generated file.

**The connection-side change that enables this:**

- The connection form now allows ticking **"Module-only Sage connection"**, which makes the sync query field optional. JTI's pool doesn't need a sync query (it reads on demand, not by sweeping into `datarecord`); previously you couldn't create a connection without one. Same flag also opts the connection out of the global scheduled-sync sweep.

### Monthly automation

Exports for full calendar months get archived to disk. This is the part that means nobody has to remember to run the export.

**What gets archived:**

- **Scheduled monthly archive.** A cron at **02:00 site-local on the 1st of every month** generates the export for the previous calendar month and archives it. Tagged `source='scheduled'`, generated_by=`system:scheduled`.
- **Manual full-month export.** If you click Generate on the JTI page with a range that's exactly one calendar month (e.g. `2026-04-01 → 2026-04-30`), the result gets archived alongside being downloaded. Tagged `source='manual'`, generated_by=`<operator email>`. Partial-month or multi-month ranges remain download-only — they're treated as ad-hoc operator queries, not canonical artefacts.
- **Boot-time catch-up.** When the app starts, it looks back twelve months and backfills anything that doesn't have a scheduled archive yet. Runs ~45 seconds after boot so migrations and the Sage pool have settled. On the smoke-test install, the first boot after this release archived all twelve months in under a minute. If a site has been offline through a month-end, the operator doesn't need to do anything — next start, the missing month appears.
- **Re-runs.** The schema keeps the *latest* version per (year, month) on the listing UI but stores every version. If you've fixed bad data in Sage and want to regenerate April after the scheduled one already ran, the new manual export simply produces version #2 for April; the old version stays queryable. Nothing is overwritten.

**Where you see them:**

- **Past months panel** on the JTI page. Shows period, generated-at timestamp, source pill (scheduled / manual), row count, file size, and a Download button per archive. Refreshes automatically after a Generate that triggered an archive write.
- Each archive carries a sha256 of its bytes; the download endpoint returns it as `X-JTI-Archive-Sha256` so a client can verify integrity end-to-end.

**Retention:**

- Files are kept forever. Realistic footprint is ~6 MB per year per site — minimal. There is no automatic prune.
- Files live under `uploads/jti-archive/<YYYY>-<MM>/<id>-<filename>` on the site's disk. SQLite metadata in the new `jti_archive` table.

### Site ↔ Hub: archives flow upstream automatically

For multi-site deployments, every archived export is sent to the hub without operator action.

**Push, as the primary path:**

- Immediately after a successful archive write (either a manual full-month or the scheduled run), the site fires a non-blocking push to the hub at `POST /api/hub/receive-jti-archive`. Auth uses the existing per-site `x-reporting-token` header — same model as the existing notify-backup-ready flow.
- The push is fire-and-forget: the operator never waits on it during a download, and a push failure does not block the download.
- A site without `HUB_URL` / `REPORTING_TOKEN` env vars set marks each archive as `skipped_no_hub` — no retries, no logs after the first, no surprise behaviour. This is the expected state on standalone-site installs.

**Retry tick for failures:**

- Every 15 minutes, the scheduler scans for archives in `pending` or `failed` state and re-attempts the push, batched 10 per tick. Capped at 50 attempts per row — past that, the operator sees it stuck in the UI's "Past months" panel (red Failed pill with hover-tooltip showing the last error) and can investigate manually rather than have the log spam them forever.

**Pull-fallback, as the safety net:**

- On hub installs, a daily cron at **03:30** asks every site for its archive list (`GET /api/reporting/jti/archives`) and fetches any sha256 the hub doesn't already have. This catches anything the push missed — a site that was offline at month-end, a hub that was down during the push, an `x-reporting-token` typo that took a week to fix.
- Dedup is enforced by a database UNIQUE index on `(site_id, sha256)`. A push followed by a pull-fallback that targets the same bytes is idempotent; the second arrival returns 200 with the existing hub id.

**Where the hub operator sees received archives:**

- New **JTI** page in the hub sidebar (hub mode only). Lists every received archive across all sites, latest first.
- Filter chips at the top let you narrow to one site.
- Each row shows: site_id, period, received-at timestamp, source pill (scheduled / manual), **via pill (push / pull)** so an operator can see at a glance whether the push worked or the pull-fallback saved the day, row count, file size, Download button.
- The download streams the original bytes back (sha256-verified at receive time, so what you download is what the site originally archived).

### Operations → Schedule tab

A small but persistently asked-for view: what is the system scheduled to run, and when's the next time?

- New **Schedule** tab on the Operations page (admin-only, same gate as Job Runs).
- Lists every background job the scheduler registered at boot — sixteen entries on a typical site install, including the new JTI ones. Each row: name, type (cron / interval / one-shot), mode gate (site / hub / both), human-readable schedule with the raw cron expression on hover, next computed fire time, and a "in 3h" / "in 12d" relative-time chip.
- Cron jobs use node-cron's native `task.getNextRun()` — no parser dependency, the next-fire time stays accurate across DST transitions.
- Sorted with soonest-future fire first. Past one-shots (the boot catch-ups) sink to the bottom; intervals (no concrete next-fire) sit at the very bottom.
- Pairs cleanly with the existing Job Runs tab: Schedule shows what *will* run, Job Runs shows what *has* run.

For the question that started this view: yes, the JTI monthly export shows up as
`jti-monthly-export   cron   site   0 2 1 * * (1st of every month at 02:00)   next: <ISO timestamp>`
and the auto-archived June run will land at `2026-06-01 02:00 site-local`.

## New database migrations

All idempotent (`CREATE TABLE IF NOT EXISTS` plus `CREATE INDEX IF NOT EXISTS`). Apply on first boot of this release.

| Version | Name | Effect |
|---|---|---|
| **v69** | `jti_export_permission_and_settings` | Adds `can_access_jti` column to `user` (default 0); creates `jti_settings` key-value table holding the per-install address defaults + the optional admin SQL override. |
| **v70** | `jti_archive_table` | Creates `jti_archive` — one row per generated export, indexed by `(period_year DESC, period_month DESC, generated_at DESC)` for the listing UI and by `hub_push_status` for the retry tick. Includes hub-push state-machine columns (`hub_push_status`, `hub_push_at`, `hub_push_error`, `hub_push_attempts`). |
| **v71** | `hub_jti_archive_table` | Hub-side mirror table. Dedup enforced by `UNIQUE(site_id, sha256)`. Captures push-vs-pull provenance in `received_via`. Indexed for "latest period across all sites" and "per-site latest period" queries. |

## New environment variables

None.

The existing `HUB_URL`, `REPORTING_TOKEN`, `SITE_ID`, and `HUB_MODE` are all the module needs. On a site install with no hub configured, the JTI module works in standalone mode; archives stay on the site disk and the push state machine settles into `skipped_no_hub`.

## New permissions flag

| Flag | Default | Effect |
|---|---|---|
| `can_access_jti` | off (0) | Required to see the JTI sidebar entry and use any `/api/jti/*` or `/api/hub/jti/*` endpoint. Admins pass unconditionally per the existing permission gate. Toggle per-user under Settings → Users → permissions. |

## Suggested deploy order

This release is internally consistent — the whole branch lands as one unit. There's no "partial JTI" intermediate state.

1. **Apply the release.** Migrations v69 → v70 → v71 run on first boot.
2. **Assign a Sage connection to JTI.** Open Settings → Connections → Module routing. Find the **JTI export** dropdown. Pick the company-data Sage connection (CARDAT, ERMDAT, etc.). Without this, the JTI page shows a yellow "not yet routable" banner and the export endpoint returns 503 with the exact message the operator needs to act on.
3. **Save the per-install defaults.** Open the JTI page → "Install defaults" panel. Fill TownCity / Region / Country / Site label. Save. (Without these, the export still runs but address fields come out blank and the filename uses "Unknown" for the site.)
4. **Grant `can_access_jti` to the operators who need it.** Settings → Users → permissions modal.
5. **Verify the schedule.** Operations → Schedule tab. Confirm `jti-monthly-export` shows the right next-fire time for your timezone.
6. **(Hub installs)** Confirm `HUB_SITES` env var includes the new site if this is a fresh install. Existing hubs already have the entry — nothing changes there.

## Operator smoke tests post-deploy

Run these after the release lands. Each is one click or one curl; covers the highest-value regression surface.

- **Permissions gate.** Log in as a non-admin user *without* `can_access_jti`. Open the URL `/jti` directly — should redirect or show "no access". The sidebar should not show the JTI entry.
- **Pool routing.** Without assigning a connection, click Generate on the JTI page. Should fail with a 503 surfacing the exact "Settings → Connections → Module routing → assign a connection to JTI export" message. Then assign the connection. Generate again. Should succeed.
- **Round-trip integrity.** Generate a full-month export (e.g. 1st to last day of last month). Open the Past months panel — the new row should appear with a Download button. Click Download. The downloaded bytes' sha256 should match the row's stored sha256 (visible in the `X-JTI-Archive-Sha256` response header on the download endpoint).
- **Auto-archive on full month.** Click Generate with a clean `YYYY-MM-01` → `YYYY-MM-{lastDay}` range. Confirm a new archive row appears. Then click Generate with a *partial-month* range. Confirm **no** new archive row appears.
- **Boot catch-up.** Restart the app. Watch System Log for `[jti-scheduler] catch-up archived` lines — there should be either one per missing month, or `boot catch-up: nothing to backfill` if everything's already covered. The first boot of this release on an existing site will produce up to twelve archive rows.
- **Schedule view.** Operations → Schedule tab → look for `jti-monthly-export`. The "When" column should show the next 1st-of-month at 02:00.
- **(Hub installs)** After at least one push has fired from a site, open the hub-side JTI page. Confirm the row shows `via: push` (not `pull`). If the site was offline at push time, the daily 03:30 pull-fallback will fill the gap; next-day view should show `via: pull` for those rows.
- **(Standalone site, no HUB_URL)** Generate a full-month export. Open Past months. The Hub pill on the row should read "No hub" — that's the `skipped_no_hub` state, not an error.

## Notes for the next operator who touches this

- **The site's "Last Week Paid" tile and the hub's mirror are kept in lockstep** by routing both through one helper (see the 2026-05-08 release notes). The JTI archives follow the same pattern: the site's row is the source of truth; the hub's row is a mirror that dedups by sha256. If you find yourself writing a parallel `SELECT` over hub_jti_archive that derives a value the site already computes, route both through one helper instead.
- **The merge button stays with you.** As with every release, no PR was merged by automation. The branch sits on `feat/jti-export` and is ready when you are.
